# Telegram-бот для знакомств

Самостоятельный Python-проект. Бот и веб-админка работают в Docker, данные —
в PostgreSQL. Telegram API доступен через существующий Cloudflare Worker из
соседнего репозитория `telegram-api-proxy`; менять или деплоить Worker для
этого обновления не требуется.

## Что умеет первая версия

- Регистрация в личном чате: подтверждение 18+, парень / девушка, возраст
  18–100, одно фото, описание до 500 символов. Имя берётся из Telegram.
- Несколько целей: отношения / свидание, друзья, компания, проект, интересы.
- Предпросмотр и сохранение анкеты. Черновик каждого шага сохраняется в БД
  и восстанавливается через `/start` после перезапуска.
- Просмотр активных чужих анкет, у которых есть хотя бы одна общая цель.
  Свою анкету, скрытые анкеты и уже оценённые карточки бот не показывает.
- Лайк или пропуск. При взаимном лайке оба получают контакт; последние
  50 совпадений доступны через `/matches`. Если уведомление не доставлено,
  совпадение остаётся в базе и в этом списке.
- Редактирование, скрытие / включение показа, удаление с подтверждением.
  Изменения заменяют старую анкету только после сохранения. Удаление
  убирает анкету из бота и удаляет связанные лайки / пропуски; содержимое
  анкеты и текущего черновика сохраняется в закрытом архиве администратора.
- Админка: список, поиск по имени / username / Telegram ID, фильтры по статусу,
  пагинация, карточки с фото и целями, архив всех удалений, блокировка /
  разблокировка пользователя с обязательной причиной и историей действий.

Пока нет геопоиска, фильтра по полу или возрасту партнёра, чата внутри бота,
предварительного одобрения анкет, жалоб, нескольких фото и проверки реального возраста. Совпадение
целей «интересы» не означает совпадение конкретных хобби: отдельных тегов пока нет.
18+ и правила взаимных лайков приняты как исходные настройки первой версии.

## Дашборд, события и настройки

Главная страница админки теперь открывает дашборд (`/admin/dashboard`); текущие
анкеты находятся на `/admin/profiles`, настройки — `/admin/settings`. В анкетах доступен
переход к архиву. Авторизация, SSH-туннель и пароли остались прежними.

На дашборде можно выбрать период до 366 дней включительно. Все дни считаются
по Москве (UTC+3). Есть график и таблица дневной активности, источники,
воронка, D1/D7 по когортам, основные действия, сессии, технические показатели,
список последних ошибок и выгрузка дневных показателей в CSV.

В разделе **Пользователи** (`/admin/users`) доступны Telegram ID, последнее известное
имя и username, первый и последний источник, даты действий и число `/start`.
Есть поиск по ID / имени / username, фильтр активных за период и переходы
к анкете и архиву. Учитываются также люди без анкеты и удалившие её.
При обновлении имена переносятся из имеющихся анкет, черновиков и архива;
затем обновляются из Telegram при каждом действии. Неизвестные значения
показаны прочерком. Изменение username не создаёт нового пользователя.

### История конкретного пользователя

Нажмите Telegram ID в разделе **Пользователи**, либо ссылку **Действия и
попытки пользователя** в текущей анкете или архиве. Страница `/admin/users/ID`
доступна под тем же паролем администратора и показывает:

- Все попытки заполнения: начало, пройденные шаги, ожидаемый шаг,
  публикацию, отмену, перезапуск и удаление. Редактирования, повторные
  анкеты и старые черновики отмечены отдельно.
- Ленту входящих действий и результатов: `/start` с источником, доставку
  карточек, лайки, пропуски, взаимные симпатии, скрытие и удаление.
  Взаимная симпатия видна у обоих участников.
- Сессии с началом, последним действием, длительностью и числом действий.
- Ошибки обработки и Telegram API, включая неуспешную отправку этому
  пользователю по действию другого участника. Один сбой может дать две
  записи на разных уровнях; суммировать их как отдельные инциденты нельзя.

По умолчанию открывается вся сохранённая история. Можно выбрать период
до 366 дней; время указано по Москве. Попытки отбираются по дате начала,
их прогресс показан на текущий момент. Сессии, пересекающие период,
показаны целиком. У каждого раздела своя пагинация по 30 записей.
История доступна после удаления анкеты, начиная с установки аналитики.
Тексты сообщений и фотографии в ленте не сохраняются.

### Как определены показатели

- Уникальный пользователь — Telegram ID. Активность — входящее сообщение
  или callback-кнопка в личном чате от человека. Группы, сообщения ботов,
  просмотры админки и исходящие уведомления не увеличивают активность.
- DAU — уникальные за выбранный последний день; WAU — за 7, MAU — за 30
  календарных дней до этой даты включительно. Текущий день ещё неполный.
- Новая сессия начинается при разрыве **не менее 30 минут** между действиями.
  Состояние сессий сохраняется в БД и переживает перезапуск. Длина сессии —
  время между первым и последним действием, без дополнительных 30 минут;
  сессия с одним действием имеет длительность 0, что не означает отказ.
- `/start` разделён на первый **наблюдаемый** и повторные. Источник каждого
  запуска — метка `?start=...`; первый источник не перезаписывается повторным.
  Новые пользователи в таблице источников относятся к первому наблюдаемому
  `/start`; без него источник `unknown`. Метки не являются доказательством
  рекламного перехода: пользователь может вручную отправить такую команду.
- Примеры ссылок: `https://t.me/ITMO_connectbot?start=itmo_chat` и
  `https://t.me/ITMO_connectbot?start=poster_october`.
  Метка содержит 1–64 символа A–Z, a–z, 0–9, `_`, `-`. Служебные значения:
  `direct` — без метки, `invalid` — некорректный параметр, `unknown` — источник
  ещё неизвестен. Эти три значения не используйте как названия кампаний.
- Воронка — **попытки** создания первой анкеты, начатые в периоде, и их текущий
  прогресс. Каждый принятый шаг фиксируется при сохранении в БД. Повторные
  переключения целей не создают повторное завершение шага. Редактирование,
  повторная регистрация после удаления и незавершённые старые анкеты
  исключены из воронки первой анкеты. Один человек может начать несколько
  попыток; это не воронка уникальных пользователей.
- Незавершённые попытки без действий 24 часа показаны по последнему шагу.
  Это сигнал возможного ухода, не доказанный отказ. Отмена, перезапуск и
  удаление показываются отдельно. Прогресс попытки может измениться позже
  выбранного периода, если человек вернулся и закончил анкету.
- Карточка считается просмотренной только после успешного ответа Telegram
  на отправку. Прочтение человеком неизвестно. Лайк / пропуск, публикация,
  скрытие и удаление считаются после изменения данных, а не просто нажатия.
- Взаимная симпатия — одно событие при втором лайке. Повторное нажатие не
  даёт дубля. После удаления и новой регистрации та же пара может создать
  новое событие. Доля активных с совпадением считает обоих участников,
  но только тех, кто был активен в выбранном периоде.
- D1/D7 — доля новых пользователей, совершивших действие **ровно на 1-й / 7-й
  календарный день** после первого наблюдаемого действия. Не rolling retention.
  День возврата должен полностью закончиться; иначе показывается «Ещё рано».
  Общий процент взвешен по численности только зрелых когорт.
- Дополнительно: доля лайков среди оценок, доля пустых выдач, медиана времени
  до первой публикации новых пользователей, ошибки валидации анкеты,
  устаревшие кнопки, возобновления заполнения, события модерации.

### История и технические ограничения

Сбор начинается с **миграции 3**. Она отмечает существующие ID из анкет,
черновиков и архива как известных до обновления. Их последующая активность
учитывается, но они не считаются новыми когортами. Даты старых `/start`,
просмотров и сессий не восстанавливаются. Если человек раньше взаимодействовал,
но никаких следов в старой БД не осталось, отличить его от нового невозможно.

Одинаковый Telegram `update_id` не обрабатывается повторно. Успешные изменения
анкеты и их события записываются в одной транзакции. Аналитика не удаляется
при удалении анкеты. Тестовые действия и действия владельца также учитываются.
Проект рассчитан на один токен бота и один polling-процесс на БД.

Время обработки включает обращения к БД и отправку ответов, но не ожидание
long polling. Показываются p50 и p95. Вызовы Telegram API учитывают метод,
длительность, успех / тип ошибки, канал bot или admin и при наличии ID
получателя. Успешные `getUpdates` не сохраняются; ошибки polling сохраняются.
Неуспешные `sendMessage` / `sendPhoto` включают и ошибки уведомления о совпадении,
которые перехватывает обработчик. Ошибка API и вызванная ей ошибка обработчика
показаны раздельно — их нельзя складывать как независимые происшествия.

Текст сообщений, описания анкет, фотографии, токены, URL и сообщения исключений
в события не копируются. Сохраняются ID, коды действий и необходимые параметры.
Учёт действий упомянут в тексте регистрации. Автоматического удаления истории
событий пока нет; нужно следить за размером БД и резервных копий.

Открытие чата, прочтение, переход по ссылке без доставленного `/start` не видны.
При падении процесса или БД полной гарантии записи нет: незавершённый update
остаётся в состоянии `processing`, а его повторная доставка не повторяет
действие автоматически. Проверяйте логи `analytics_finish_failed` и
`analytics_telegram_failed`. Это не внешняя система мониторинга доступности.

### Настройки

Можно приостановить **начало новых анкет**. Уже начатые черновики разрешено
завершить, существующие анкеты — изменить. Изменение применяется сразу,
записывается с именем администратора и событием `settings_changed`, защищено
авторизацией и CSRF. Новых переменных `.env` не требуется. Правило сессий,
часовой пояс и определения метрик показаны как фиксированные параметры,
чтобы их переключение не меняло смысл истории. Настройки премодерации пока нет.

Таблицы для просмотра в DBeaver:

| Таблица | Содержимое |
| --- | --- |
| `analytics_users` | Первый / последний визит, источники, число запусков |
| `analytics_sessions` | Сессии и количество входящих действий |
| `analytics_updates` | Дедупликация, результат и длительность обработки |
| `analytics_activity_days` | Уникальные активные дни пользователя по Москве |
| `analytics_attempts` | Попытки заполнения, пройденные шаги и финальный статус |
| `analytics_events` | Продуктовые события и вызовы Telegram |
| `app_settings` | Приём новых анкет и информация об изменении настроек |

Источники: [Telegram deep links](https://core.telegram.org/bots/features#deep-linking),
[aiogram client middleware](https://docs.aiogram.dev/en/latest/api/session/middleware.html).

## Фото

Пользователь отправляет фотографию боту. В PostgreSQL хранится Telegram
`file_id`, а не файл и не публичная ссылка. Фото остаётся на серверах Telegram;
это не хранение на телефоне пользователя. Для показа в боте повторно используется
`file_id`, привязанный к этому боту. При смене бота старые идентификаторы не следует
считать переносимыми.

В админке браузер обращается к защищённому маршруту `/profiles/ID/photo`.
Сервер вызывает `getFile` и скачивает фото через тот же авторизованный Worker,
передавая его браузеру из памяти (не более 10 МБ). На диск фото не сохраняется;
токен бота, секрет прокси и Telegram URL не отправляются браузеру.
При удалении `file_id` остаётся в архивной копии; фото доступно администратору
через защищённый маршрут `/archive/ID/photo`. Доступность файла по-прежнему
зависит от Telegram. Удаление не стирает сообщения или файлы из Telegram.

## Запуск на сервере

Нужны Docker Engine и Docker Compose v2.

```bash
cp -n .env.example .env
nano .env
chmod 600 .env
docker compose up -d --build
docker compose logs --tail=100 -f bot admin
```

Переменные `.env`:

| Переменная                      | Значение                                        |
| ------------------------------- | ----------------------------------------------- |
| `BOT_TOKEN`                     | Токен от BotFather                              |
| `TELEGRAM_API_BASE`             | HTTPS-адрес существующего Worker без пути       |
| `TELEGRAM_PROXY_SECRET`         | Значение `PROXY_SECRET` в Cloudflare            |
| `POSTGRES_DB` / `POSTGRES_USER` | По умолчанию `dating`                           |
| `POSTGRES_PASSWORD`             | Отдельный случайный пароль БД                   |
| `ADMIN_USER`                    | По умолчанию `admin`                            |
| `ADMIN_PASSWORD`                | Отдельный случайный пароль, минимум 16 символов |
| `ADMIN_BIND` / `ADMIN_PORT`     | По умолчанию `127.0.0.1` и `8080`               |

Для генерации пароля: `openssl rand -hex 32`. В текущий локальный `.env`
уже добавлены отдельные случайные пароли БД и админки; существующие настройки
Telegram сохранены. При переносе можно безопасно скопировать этот `.env`
или заполнить новый. Секреты не входят в Git, образ или контекст сборки.

Compose запускает `db`, `bot`, `admin`. PostgreSQL не публикует порт на хост,
данные находятся в именованном томе `postgres_data`. Бот и админка ждут
готовности БД; таблицы создаются автоматически с блокировкой параллельной
инициализации. Приложения работают без root, с read-only filesystem и
ротацией логов. Перезапуск контейнеров автоматический; Docker на сервере
должен быть включён в автозагрузку.

Перед запуском остановите старую версию бота с тем же токеном.
Один токен — один polling-процесс. Установленный webhook нужно удалить
перед polling; приложение не удаляет его автоматически.

## Как открыть админку

ssh -N -o ExitOnForwardFailure=yes -L 18080:127.0.0.1:8080 mshkss@164.215.68.43

На том же компьютере: **http://127.0.0.1:8080**. Браузер спросит логин и пароль
из `ADMIN_USER` / `ADMIN_PASSWORD`. Это HTTP Basic Auth, а не секретный URL.
В этой версии нет пользователей админки, ролей и формы выхода: для окончания
сеанса закройте приватное окно браузера. После 10 неудачных запросов с одного
адреса доступ ограничивается на минуту; счётчик хранится в памяти процесса.

Для сервера проще оставить `ADMIN_BIND=127.0.0.1` и с компьютера открыть туннель:

```bash
ssh -N -L 18080:127.0.0.1:8080 user@SERVER_IP
ssh -N -o ExitOnForwardFailure=yes -L 18080:127.0.0.1:8080 mshkss@164.215.68.43
```

Затем откройте **http://127.0.0.1:18080/admin/**. Пароль и данные идут через SSH;
публичный порт админки открывать не нужно.

Для доступа по внешнему домену поставьте HTTPS reverse proxy на том же сервере
перед `127.0.0.1:8080`. Например, при установленном Caddy и настроенном DNS:

```caddyfile
admin.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Замените домен своим; HTTPS-сертификат и порты 80/443 обслуживает Caddy.
Не открывайте Basic Auth наружу по обычному HTTP. При reverse proxy лимит
попыток общий для его IP; реальные клиентские заголовки намеренно не доверяются.

## Команды бота

| Команда           | Действие                                                    |
| ----------------- | ----------------------------------------------------------- |
| `/start`          | Меню или продолжение черновика                              |
| `/profile`        | Моя сохранённая анкета                                      |
| `/edit`           | Заполнить заново; старая анкета сохранится до подтверждения |
| `/cancel`         | Отменить черновик                                           |
| `/browse`         | Следующая подходящая анкета                                 |
| `/matches`        | Последние взаимные лайки                                    |
| `/hide` / `/show` | Скрыть / включить показ                                     |
| `/delete`         | Удаление с подтверждением                                   |

Цели не являются фильтром пола: парень или девушка — характеристика своей
анкеты. Контакт после совпадения использует стабильный Telegram ID, поэтому
смена username не перенаправляет к другому человеку. Доступность профиля
зависит от настроек приватности Telegram. Текст и фото пользовательской
анкеты могут сами содержать контакты; бот их автоматически не удаляет.

## Админка через Nginx и HTTPS

Публичный адрес: **https://anatolii-botov.ru/admin/**. Префикс по умолчанию —
`/admin`; все ссылки, формы, фото, выгрузка CSV и перенаправления используют
его. Поддерживаются оба варианта `proxy_pass`: с удалением префикса и с
его сохранением. Заголовки Host / X-Forwarded-Prefix не меняют префикс.
Внутренние маршруты без префикса сохранены для Nginx, который его удаляет.
Порт приложения остаётся привязанным к localhost.

Текущий пользовательский блок Nginx с `proxy_pass http://127.0.0.1:8080/;`
совместим с обновлением. Образец — [deploy/nginx-admin.conf](deploy/nginx-admin.conf):
это только два `location`, которые размещаются **внутри существующего HTTPS
server-блока**, а не замена конфигурации Certbot. При изменении Nginx:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

В `.env` на сервере:

```dotenv
ADMIN_BASE_PATH=/admin
ADMIN_BIND=127.0.0.1
ADMIN_PORT=8080
ADMIN_TRUSTED_PROXIES=127.0.0.1/32,::1/128
```

Для реального IP в журнале приложение доверяет `X-Real-IP` **только** от IP,
перечисленных в `ADMIN_TRUSTED_PROXIES`. Nginx должен перезаписывать его через
`proxy_set_header X-Real-IP $remote_addr;` — в текущей конфигурации это уже есть.
В Docker приложение обычно видит соединение от шлюза сети, а не от loopback.
Узнать адрес шлюза работающего контейнера (из папки проекта):

```bash
sudo docker inspect "$(sudo docker compose ps -q admin)" --format '{{range .NetworkSettings.Networks}}{{.Gateway}}{{println}}{{end}}'
```

Если результат, например, `172.18.0.1`, добавьте **этот фактический адрес**:

```dotenv
ADMIN_TRUSTED_PROXIES=127.0.0.1/32,::1/128,172.18.0.1/32
```

Не копируйте пример IP без проверки и не указывайте `0.0.0.0/0`.
После запуска в журнале видны и IP клиента, и IP соединения. Если там адрес
Docker и пометка «прямое соединение», проверьте адрес доверенного прокси.
При изменении сети Docker настройку нужно обновить. За внешним CDN понадобится
отдельная корректная настройка real IP в самом Nginx; приложение доверяет только
одному `X-Real-IP` и не использует клиентский `X-Forwarded-For`.

После переноса кода и сохранения `.env`:

```bash
cd /opt/telegram-greeting-bot
sudo docker compose up -d --build
sudo docker compose logs --tail=100 admin
```

Миграция 6 автоматически создаёт `admin_access_events`. Авторизация остаётся
Basic Auth с существующими `ADMIN_USER` / `ADMIN_PASSWORD`. Через SSH-туннель
страница теперь открывается по `http://127.0.0.1:18080/admin/`.
Для отдельной установки без префикса можно явно задать `ADMIN_BASE_PATH=`.

### Журнал входов

Меню **Журнал входов** → `/admin/access-log`. Хранятся время, результат,
имя администратора при успешной авторизации, IP клиента и соединения,
User-Agent и шаблон маршрута. Есть фильтр по результату и страницы по 50 записей.
В PostgreSQL журнал сохраняется после перезапуска; события также выводятся
в Docker-логи как JSON с `event=admin_auth`.

У Basic Auth нет отдельного события отправки формы входа. Успех фиксируется
на первом авторизованном запросе пары IP + User-Agent после ≥30 минут
бездействия. Перезагрузки страниц и фото внутри этого интервала не дают
новых «входов». После перезапуска админки, смены IP или браузера будет новая
запись. Несколько людей за одним IP с одинаковым User-Agent могут объединиться.
Кэш посещений ограничен 4096 записями; вытесненная запись также даст новый вход.
Это наблюдаемые посещения, а не идентификация физических лиц.

Запрос без Authorization, неверные данные и ограничение попыток имеют
отдельные результаты. После 10 неуспешных запросов с одного IP за минуту
приложение возвращает 429; срабатывание записывается один раз за окно.
Счётчики находятся в памяти одного процесса админки и сбрасываются при рестарте.
Пароли, Authorization, содержимое форм и query-параметры не записываются.
Автоматической очистки журнала нет. Если запись в БД не удалась, событие остаётся
в Docker-логе, дополнительно выводится `admin_audit_write_failed`; авторизация
продолжает работать. Запросы, отклонённые самим Nginx до приложения, видны только
в логах Nginx.

## Архив удалённых анкет и модерация

В верхнем меню админки появился **«Архив удалённых»** (`/admin/archive`). Каждое
удаление сохраняет отдельный неизменяемый снимок: Telegram ID, username,
имя, пол, возраст, описание, цели, `file_id`, даты и текущий черновик, если он
был. Если сохранённой анкеты ещё нет, сохраняется незавершённый черновик.
Повторная регистрация и новое удаление создают новую запись; старые остаются.
Повторное нажатие удаления без новой анкеты не создаёт дубль.
Отмена черновика через `/cancel` и перезапуск заполнения через `/edit` сами
по себе не создают архивные записи: архив фиксирует подтверждённое удаление.

Архив не виден участникам и не участвует в поиске и совпадениях. Копирование
в архив и удаление текущей анкеты выполняются одной транзакцией: если архив
не сохранился, исходная анкета тоже не удалится. Автоматической очистки архива
нет. Пользователь предупреждён о сохранении копии при регистрации и перед
подтверждением удаления. Ранее удалённые старой версией анкеты восстановить
из текущей базы невозможно; миграция сохраняет только имеющиеся данные.

В текущей или архивной карточке есть блок **«Модерация пользователя»**:

- «Заблокировать пользователя»: обязательная причина, 1–500 символов.
- «Разблокировать пользователя»: обязательная причина снятия блокировки.
- Журнал: действие, причина, имя администратора и время UTC. Интерфейс
  показывает последние 50 действий, база хранит всю историю.

Блокировка привязана к Telegram ID и сохраняется после удаления, создания
и изменения анкеты. Заблокированный пользователь не может просматривать
анкеты, ставить лайки или получать контакты через совпадения; его анкета
также исключена из этих выдач. Он может исправить или удалить свою анкету,
но `/show` и повторная регистрация не снимают блокировку. Причина видна
пользователю при попытке поиска или просмотре своей анкеты; отдельная
рассылка уведомлений при действии модератора не выполняется.
Разблокировка сохраняет пользовательский выбор скрыть анкету и не
восстанавливает удалённую. Уже отправленные сообщения Telegram не стираются.

Модерация выполняется POST-запросами с авторизацией и подписанным CSRF-токеном
формы, действующим один час. После перезапуска админки или истечения срока
обновите страницу перед отправкой. Изменение БД и запись в журнал атомарны.

Для обновления работающего сервера сначала перенесите новый код, затем
в папке проекта выполните (том PostgreSQL сохраняется):

```bash
docker compose stop bot admin
docker compose up -d --build
docker compose logs --tail=100 bot admin
```

Миграция применится автоматически. Оба приложения нужно обновить вместе:
старая версия бота продолжает удалять анкеты без архива и не знает блокировок.
Перед обновлением можно сделать резервную копию по инструкции ниже.

## Обновления и резервное копирование

```bash
docker compose up -d --build      # применить код и .env
docker compose ps
docker compose down              # остановить, сохранив данные
```

**Не используйте `docker compose down -v`, если хотите сохранить анкеты.**
Пароль PostgreSQL применяется образом при создании тома; его изменение
в `.env` не меняет пароль уже существующего пользователя БД.

Резервная копия (содержит персональные данные):

```bash
umask 077
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup.sql
```

Восстановление в пустую БД с остановленными приложениями:

```bash
docker compose stop bot admin
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" "$POSTGRES_DB"' < backup.sql
docker compose up -d bot admin
```

Не храните резервные копии в Git. Архив удалённых анкет и история модерации также входят в резервную копию.

## Локальная разработка и проверки

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m unittest discover -s tests -v
docker compose config --quiet
```

Интеграционные тесты создают **отдельный временный PostgreSQL** и удаляют его
после проверки; рабочая БД не используется. Для них нужны `initdb` и `pg_ctl`
в PATH либо `TEST_POSTGRES_BIN=/path/to/postgresql/bin`. Без этих утилит
интеграционные тесты пропускаются. На этом компьютере автоматически используется
установленный PostgreSQL 15 из Homebrew; Compose настроен на PostgreSQL 17.

Для запуска без Docker нужен доступный PostgreSQL. Укажите его параметры в
`.env` и запустите отдельно `python bot.py` и `python -m app.admin`.
Админка без Docker слушает `127.0.0.1:8080`. В Compose адрес БД и внутренний
интерфейс админки задаются автоматически.

`app/db.py` содержит стартовую схему и версионированные миграции.
Применённые версии записываются в `schema_migrations`; миграция архива и
модерации имеет версию 2, аналитики — 3, имён пользователей — 4, индексов
персональной истории — 5, журнала входов — 6. Миграции выполняются в транзакции под общей
блокировкой, поэтому одновременный старт бота и админки безопасен. В первой версии один polling-процесс обрабатывает
обновления последовательно; для большой нагрузки это нужно пересмотреть.

Источники: [Telegram file_id и getFile](https://core.telegram.org/bots/api#getfile),
[свой API-сервер в aiogram](https://docs.aiogram.dev/en/latest/api/session/custom_server.html).

Маршрутизация Nginx: [официальная документация proxy_pass](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass).
